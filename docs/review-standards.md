# 代码评审规范（Review Standards）

适用于所有 PR 的提交自查与人工评审。目标：**小而可审**的变更 +
**证据驱动**的评审。参考 qwen-code 的 PR/评审实践，按本仓库体量裁剪。

## 1. PR 准入门槛（提交前自查清单）

不满足任一条，不要点"Create pull request"：

1. **对应 issue 存在**，PR 描述中链接（`Fixes #N` / `Closes #N` / `Ref #N`）。
2. **变更分级正确**：按 [workflow.md](workflow.md) 第 1 节矩阵，该有的 design/plan
   已在**同一 PR 或前置 PR** 中存在。行为变更无设计文档 = 直接打回。
3. **`mvn verify` 本地全绿**（与 CI 同一条命令）。
4. **PR 遵循模板** [.github/pull_request_template.md](../.github/pull_request_template.md)：
   动机（为什么）→ 变更（做了什么，面向行为而非逐文件罗列）→ 验证（跑了什么，
   结果如何）→ 风险/影响。
5. **golden 基线同步**：若模型文件变化，基线数字与再生成在同一 commit（见
   [testing-standards.md](testing-standards.md) 第 4 节），PR 描述给出新旧对比。
6. **自审完成**：通读完整 diff（含新文件）至少一遍，确认无调试残留、无被注释的
   死代码、无无关格式化噪声。
7. **一个 PR 一件事**：混合了功能 + 无关重构的 PR 拆开。约 1200 行改动开始考虑拆分；
   超过约 2000 行必须拆分或在描述中解释为何必须一起落地。
8. **文档同步**：用户可见行为变化已更新 README；架构/契约变化已更新
   [architecture.md](architecture.md)。

## 2. 评审者的检查重点（按优先级）

本仓库特有的评审顺序，先高后低：

1. **行为契约是否被破坏**（对照 [architecture.md](architecture.md) 第 4 节的契约表）：
   - 字符串状态协议（`toString` 家族）格式有没有变？
   - `preCheck`/`postCheck` 返回语义与调度路径有没有变？
   - `graph/` 是否保持了零业务依赖？
2. **golden 基线漂移是否被正确解释**：数字变化没有解释 = 要求补充，不是猜。
3. **测试是否真的测了改动**：
   - 新行为的断言存在吗？断言的方向对吗（绿 ≠ 对）？
   - bug 修复的测试在修复前会红吗（PR 验证记录里应有证据）？
   - 有没有测试被悄悄修改断言/删除？
4. **已知缺陷清单不恶化**：[CODE_REVIEW.md](../CODE_REVIEW.md) 列出的问题（硬编码覆盖、
   错误模型、匹配口径等），新代码是否让它们更难修复？评审中发现的**新的**未修复问题，
   要求作者追加到 CODE_REVIEW.md 或开 issue，不允许"口头记录"。
5. **风格符合 [coding-standards.md](coding-standards.md)**：新代码无 `System.out`、
   日志级别合理、命名符合约定、Java 8 语法内。
6. **设计文档与实现一致**：design 存在时，实现与文档的决策/范围是否一致；
   偏离是否在 PR 中说明了理由。

## 3. 严重级别约定

| 级别 | 含义 | 处理 |
| ---- | ---- | ---- |
| **Critical** | 破坏正确性/一致性检查语义/数据（golden 意外漂移、契约破坏） | 必须修复后才能合并 |
| **Major** | 明确缺陷但当前场景可绕过；测试缺失到无法证明行为 | 应修复，可讨论拆后续 PR |
| **Suggestion** | 风格、命名、注释、重构建议、文档润色 | 作者裁量；拒绝需一句理由 |

"缺一个测试"默认是 Suggestion，除非**未测路径本身就是缺陷**（对照 qwen-code 评审约定）。

## 4. 评审礼仪与效率

- 评审针对代码不针对人；给出"为什么"和期望行为，而不是只说"不好"。
- 提出问题先在**当前 commit 的代码**上核实（引用的行确实存在、没有被后续 commit 改掉）。
- 作者对 Suggestion 有最终裁量权，回复一句事实理由即可，不义务全部采纳。
- 评审轮次约 5 轮后只处理 Critical（正确性/安全/数据损失/回归），其余 Suggestion
  转后续 issue 记录，防止 PR 无限膨胀。
- 分歧升级：技术分歧回 issue/设计文档层讨论并记录结论，不在 PR 评论里无限辩论。
